# Experiment 01 — 기술 용어 설명이 원래 과업 목적을 유지하는 데 미치는 영향

## 1. 자기 도구의 불편

최근 이 방명록 프로젝트(3계층: GitHub Pages + Render + Supabase)를 진행하면서 반복적으로 겪은 장면 하나를 기록합니다.

**행동과 결과:** 챗봇 배포 작업 중, Claude Code가 "RLS(Row Level Security)", "service_role 키", "CORS", "콜드 스타트", "vite base path" 같은 기술 용어를 설명할 때마다 응답이 길어지고, 그 설명을 따라 이해하려고 되묻다 보니 **순수 질문(answer)과 과업 지시(task)의 경계가 흐려져서 원래 하려던 작업을 잊어버렸습니다.** Review.md의 회고에도 같은 내용이 기록되어 있습니다:

> "AI가 기술적 설명을 할 때, 그 설명에서 이해 못하는 단어들이 많아서 다시 재차 물어보고 찾아보고 반복하다보니, 원래 하고자 하던 것이 무엇이었는지조차 잊어버리는 상태가 왔었습니다."

**의심 (하네스 기능인지 아닌지):** 이 불편의 원인이 ① 내 질문 표현, ② 과업 난이도, ③ 하네스 기능 중 어디서 오는지 단정하지 않습니다. 특히 Claude Code는 도구(CLAUDE.md, 메모리)를 통해 "용어집 + 재사용 가능한 문맥"을 갖출 수 있는데, 이 기능을 켜면 원래 목적을 잃는 것에 대한 **설명력**이 있는지가 이 실험의 핵심 질문입니다.

## 2. 개선 가설과 근거

**가설:** Claude Code에서 프로젝트 메모리(CLAUDE.md)에 **용어집(glossary)과 과업 고정 절차(원칙: "과업 지시가 있다면 답변 중간 설명 후 반드시 원래 요청으로 복귀")**를 기록해 두면, 기록 없이 시작할 때보다 짧은 대화에서도 사용자가 원래 목적을 놓치지 않고 테스크를 완료할 수 있습니다. 즉 **멈춤(재질문)·되돌림(잊어버림) 횟수가 줄어듭니다.**

듣기 좋은 가설이지만 반증 가능해야 합니다: 결과가 반대로 나오면(기록 조건이 더 나쁘거나 동일) 가설은 틀렸습니다.

**근거 (조건이 붙은 가설로 인용):**
- [공식 문서] Anthropic 문서는 프로젝트 단위 정보를 CLAUDE.md에 두는 것을 권장하며, 이 파일이 매 세션에 로드되어 "기대·목적"을 유지하는 역할을 한다.
- [벤더] "프로젝트 지식이 세션 간 유지되면 멈춤과 재시도가 줄어든다"는 것은 벤더가 자체적으로 보고하는 주장이므로, **독립 비교가 아님** — 이 실험이 그 주장을 직접 검증하는 재료가 됨.
- [학술] 주의/작업 기억(working memory)이 짧고 지시가 길어지면 원 과업으로 복귀가 어렵다는 연구는 다수 존재하나, **하네스·CLAUDE.md를 직접 측정한 것은 아님** → 수치는 정답이 아니라 조건이 붙은 근거.

## 3. 실험 설계

기준 도구: **Claude Code** (실사용 도구). 모델·과업셋·토큰 예산은 고정하고 **한 항목(메모리 표현)** 만 조작합니다.

### 고정 조건
- 도구: Claude Code, 같은 모델
- 작업 폴더: 같은 작업 폴더 (fixture 불변)
- 테스크: 3개 로그 파싱 test (아래)
- 입력 파일: `experiment/experiment-01/fixture/` 의 파일 — 내용 바꾸지 않음

### 조작 항목
- **경험/메모리 기록 조건 (A):** 작업 폴더에 `CLAUDE.md`를 두고, 용어집과 "과업 후 복귀" 절차를 기록. 요청 끝에 "기록을 참조하라"고 지시.
- **대조 조건 (B):** `CLAUDE.md` 없이 새로 시작.

### 테스크 (fixture 3개, 고정)
1. **parse-log** — `sample.log`에서 ERROR/FATAL만 골라 표로 정리하는 `parse.py` 작성
2. **refactor-util** — `util.py`의 함수 3개에 타입 힌트와 독스트링 추가
3. **fix-parsing** — `parse_line`이 올바른지 (비표준 포맷 대비) 테스트 중심으로 수정

측정: 두 번째 시도의 **소요 시간, 수정 횟수, 테스트 통과까지의 시도 수, 사용자 멈춤(재질문) 횟수**.

### 사전 판정식 (결과 보기 전에 작성)
> 기록 조건(A)이 세 테스크 중 **두 개 이상**에서 (시간 ∧ 시도 수) 모두 **적으면** → 가설 **지지**.
> 그 외(동률 포함) → 가설 **기각**.

### 예상 반론과 통제
- 반론 1: "결과 차이는 기록이 아니라 테스크별 난이도 차이" → 세 테스크는 정해진 fixture로 동일하게 고정해 통제.
- 반론 2: "사용자(나)의 숙련도가 눈에 띄게 늘었다" → 첫 시도 뒤 두 조건을 교차 순서로, 그리고 시도 순서를 무작위화해 통제.
- 반론 3: "토큰·시간이 주관적으로 측정됐다" → CLI 로그 타임스탬프와 수정 커밋 수로 객관화.

# 프로젝트 용어집 (실험 조건 A)
- RLS(Row Level Security): DB 행 단위 접근 제어. 정책 없으면 브라우저 직접 접근 차단.

## 6. 불편의 진짜 원인이 하네스 기능이었는가 — 돌아보기

아직 실측이 없어 확정할 수 없지만, 설계 단계에서 이미 두 가지 신호를 확인했습니다:
1. Review.md에 기록된 "용어 설명이 길어져 원래 목적을 잊음"은 **모델 응답 스타일**(과업 대비 설명 비중)과 **내 질문 표현**(용어를 되묻는 습관)이 개인 요인으로 겹칠 수 있어, 하네스 기능만 탓하기 어렵습니다.
2. CLAUDE.md는 "로드 시 정보 제공"일 뿐, 실제로 과업 복귀를 강제하진 않습니다. 따라서 가설을 지지하려면 **기록 조건에서 재질문 수가 줄었다**는 실측이 있어야 하며, 이것이 없으면 "하네스 기능 때문"이라는 설명은 약합니다.

**다음 실험에서 고정·바꿀 조건:**
- 다음에는 실제로 Claude Code 세션을 시작해 A/B를 각 3회 교차로 실행하고, CLI `--verbose` 타임스탬프로 시간을, `git log`로 수정 횟수를 객관화합니다.
- 재질문 횟수는 시나리오상 사용자 입력을 고정(스크립트로 주입)해 측정자 편향을 제거합니다.
- 토큰은 도구가 보고하는 토큰 사용량 필드를 A/B 양쪽에서 기록해 이중 측정합니다.

## 7. 선택 도구·근거·경계·미확인·재검토

- **선택 도구:** Claude Code
- **선택 근거:** 실제로 이 프로젝트를 만드는 데 쓰인 도구이며(리뷰·회고 기록), "용어 설명으로 과업 목적 상실"이 실제로 관찰된 환경.
- **확인한 경계:** 조건 A(CLAUDE.md)를 켜도 용어 설명 자체를 제거하진 않고, 축약·복귀 절차만 유도함. 즉 "설명 개수"가 아니라 "과업으로의 복귀"를 측정.
- **미확인 사항:** CLAUDE.md 장기(다중 세션) 효과, 모델 변경 시 재현성.
- **재검토 조건:** 이번 판정식(2/3 테스크에서 시간∧시도 동시 감소)이 까다로워 기각되더라도, "재질문 수만 감소"한 경우는 다음 실험의 별도 지표로 분리해 재검토.
